# Local memory bridge: implementation and validation

Date: 2026-09-05. Repository: Recalium working tree.

## Outcome

Implemented and installed a locally authenticated, project-scoped memory bridge with exactly three tools: retrieve_memory, ingest_memory, get_ingest_status. Both REST and MCP use the same authorization and domain service. No remote connection, tunnel, public listener, OAuth client or remote-sharing grant was configured.

The application instance under validation returned HTTP 200 with status=ok, db=ok and api_version=1. Both the REST bridge and MCP mount returned HTTP 401 without credentials. Migration 0009 is applied. The validation database started with zero bridge clients and bridge archives: the bridge starts closed and no existing memory was shared.

The read-only before/after preservation check reported identical row counts and SHA-256 fingerprints for the monitored memory tables. This included archives, jobs, summaries, facts, embeddings, FTS entries, canonical memory, links, tags and fact/tag associations. No monitored archive was ingested, deleted, changed or reprocessed during bridge validation. Two unauthenticated bridge checks appended audit events, as intended.

## Exact bridge behavior

Each credential maps to one authenticated client; clients have separate read/write grants per project. Credentials are randomly generated by the operator and only SHA-256 digests are persisted. Model and author labels remain attributed claims, distinct from authenticated identity. Unknown authority fields and identity-spoofing fields are rejected; forwarded identity headers confer no authority.

Legacy project_hint metadata is not an assignment. An archive must have an explicit bridge assignment. Orphan canonical items, mismatched canonical fact/source references, deleted sources and cross-project linked targets do not surface. A final source check runs before response serialization.

Bridge requests bypass the existing global retrieval cache entirely, even when an unrestricted cached response already contains forbidden records. Repeated retrieval remains audited. Authentication and grants are re-read for every operation; committed revocation or credential rotation affects subsequent requests. In-flight operations and permission updates are ordered by row locks. Responses already delivered cannot be retracted.

New submissions use the unchanged local_only processing policy. Summarization/extraction can use authorized local Ollama; the client cannot enable remote processing or bypass the gate. Ingestion returns acceptance, and status reports pending/completed/etc. without disclosing raw internal errors.

Idempotency keys are isolated by authenticated client and project. Payload fingerprints cover content and source metadata. Concurrent identical requests produce exactly one archive/job. Conflicting reuse returns 409. Deletion prevents replay from resurrecting a source. Simulated failure after ingestion leaves no partial archive. Success and denial/error audits contain no request content or credentials.

## Remaining boundaries and follow-up

There is no failing validation outstanding for this local milestone. Actual client credentials and project grants still need operator provisioning before everyday use. No real credentials were created or exposed during this work.

The existing local owner API/UI and legacy MCP endpoints remain trusted owner interfaces. This bridge is not an OS sandbox for an agent with unrestricted local networking, filesystem or database access. Model adapters should expose only the three bridge tools and receive no database/owner credentials.

Before remote connectivity: implement/review recipient/export permission, remote authentication, rate/resource controls and routing that exposes only the bridge. A local project read grant is not a remote-sharing grant. Existing monitored memories remain unassigned until a separately authorized sharing/migration workflow exists. No remote setup should proceed merely because the local bridge tests pass.
